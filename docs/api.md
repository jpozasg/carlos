# API

All endpoints are under http://127.0.0.1:8000 (behind the proxy, the same paths). Authentication: a session cookie (`carlos_session`, set by the login) or `Authorization: Bearer <agent token>` (admin accounts only: a normal account's token gets 403, issue #130). Every request sees only the rows of its account. Errors are JSON `{"error": "..."}` with 400 (validation, constraint), 401 (login required or wrong token), 403 (not allowed for this account), 404, 405, 415, 429 (login locked), 507 (storage quota).

## Pages
`GET /` the app, `GET /login` and `GET /invite/<token>` the sign-in page, `GET /static/...` assets, `GET /media/<listing>/<sha256>.<ext>` an archived photo (owner only).

## Sign-in and accounts
| Method and path | Body | Result |
|---|---|---|
| `POST /api/auth/login` | `{username, password}` | the account (`id`, `username`, `role`, `has_password`, `has_token`) and the session cookie; 429 after 10 wrong passwords (5 minutes) |
| `POST /api/auth/logout` | | ends the session |
| `GET /api/auth/me` | | the account, or 401 |
| `GET /api/auth/invite/<token>` | | `{username}` of a valid, unused invite |
| `POST /api/auth/invite/<token>` | `{password}` (8+ characters) | sets the password, burns the invite, signs in |
| `POST /api/account/password` | `{old, new}` | changes the password |
| `POST /api/account/token` | | admin only: `{token}`, a new agent token shown once; the previous one stops working; 403 for normal accounts |
| `GET /api/admin/users` | | all accounts (admin) |
| `POST /api/admin/users` | `{username, role?}` | creates the account with its parameters and returns `{id, username, invite}` (the invite URL) |
| `POST /api/admin/users/<id>/invite` | | a new invite link (password reset) |
| `PATCH /api/admin/users/<id>` | `{is_active?, role?}` | deactivating ends the sessions and the token; you cannot deactivate yourself |

## Writing
| Method and path | Body | Notes |
|---|---|---|
| `POST /api/preferences` | object `preference_key → value` (keys snake_case, at most 50 per call, values ≤ 1000 characters; `null` or empty removes the key) | upsert per account; returns all rows |
| `POST /api/parameters` | any subset of the parameters; `ranking_answers` (object question → answer id), `ranking_weights` (object criterion → 0–5, or `null` to go back to the answers) | validated: `annual_km`, `ownership_years`, `fuel_price_eur_l` > 0; dates ISO; `budget_ideal_eur ≤ budget_max_eur` |
| `POST /api/agent/faults`, `recalls`, `maintenance_items` | as below | (recalls: same `code`; maintenance items: same `job`, global defaults excluded; #221 phase 4) **409 `{"error", "conflict": [{id, level, level_id, part, component, …}]}`** when a similar fault (same `part`, similar `component`, overlapping `applies_from/to`) already applies to cars of the target level (#221): PATCH that row, or resend with `distinct_of: [ids]` (every conflicting id) and a `notes` reason of its own; the server prefixes the notes with "Distinct from fault #…". |
| `POST /api/agent/<table>` | a row (JSON object) | inserts; `owner_id` is set by the server; referenced parent ids must belong to the account; knowledge tables need exactly one of `vehicle_id`, `engine_id`, `generation_id`; tables in `source_required_on_insert` need `source_id`. Research (`generations`, `engines`, `vehicles`, knowledge tables, level-attached `sources`) and `listings` need an admin token (403 otherwise); admin inserts of models and level sources go to the shared catalogue. A `vehicles` POST with an `hsn`/`tsn` already in the catalogue returns `200 {id, existing: true}` and links it to the account instead of creating a duplicate |
| `PATCH /api/agent/<table>/<id>` | the changed columns | updates; `source_id` cannot be removed; `{"archived": 1}` archives a row of the knowledge tables, `unit_costs`, `valuations`, `maintenance_resets` or `inspection_items` (ignored by every read and calculation), `{"archived": 0}` restores it |
| `DELETE /api/agent/<table>/<id>` | | deletes the row and logs it in `change_log` (action `delete`); a listing goes with its own rows (captures, photos and their files, log, checklist, costs, valuations, resets); any other row is refused (400) while something references it. Agents use it only after the owner confirmed the exact deletion (AGENTS.md) |
| `POST /api/agent/media/<listing id>?url=<original>&snapshot_id=<id>` | image bytes, `Content-Type: image/jpeg|png|webp`, max 1.5 MB | archives a photo; duplicates (same hash) return `created: false` |
| `POST /api/agent/export-md` | | regenerates the account's Markdown dossiers |
| `PATCH /api/ui/inspection_items/<id>`, `POST /api/ui/inspection_items`, `POST /api/ui/listing_events`, `POST /api/ui/media/<listing id>` | `{status, notes}`, `{listing_id, item}`, `{listing_id, text}` (kind `viewing`), image bytes | the viewing mode of the phone UI; same rules as the agent API |
| `POST /api/ui/decision/<listing id>` | `{decision: shortlist|viewing|reject|reset, reason?}` | the owner's decision from the dossier: sets `verdict` ("Shortlisted by the owner", "Viewing planned by the owner", "Rejected by the owner: <reason>") and a `decision` log entry; `reject` archives the car (`WITHDRAWN`, out of the ranking), `reset` brings it back under review; not for the reference car |

Every write is recorded in `change_log` (with the writer's user id) and regenerates the account's dossiers in `data/dossiers/<account id>/`, and those of every account with a listing on a changed catalogue level.

**View as account** (issue #142): an admin's browser session with the cookie `carlos_view=<user id>` (set by the header switcher) is scoped to that account exactly like `X-Carlos-Account`, so pages and photos (`<img>` sends no headers) show it as its owner sees it. Writes while viewing: `/api/agent/`, `/api/ui/` and research requests only (logged with the admin as writer); settings, passwords and tokens are refused (403); `/api/admin/` ignores the cookie. A non-admin's `carlos_view` cookie is ignored; a cookie naming an inactive or unknown account falls back to the admin's own.

`GET /api/admin/changes?limit=50&before=<id>` (admin): the change log newest first: `id, changed_at, table_name, row_id, action, writer` (username) and `account` (the row's owner, or the owner of its listing; empty for the shared catalogue).

**The admin agent token reaches every account** (issue #143; it stays with the owner and never goes to a worker): a PATCH or DELETE of a row of another account (a listing, its rows, an account's own source or premium) and a photo upload to another account's listing are done as that account without any header; `GET /api/admin/data/<table>?owner_id=&limit=` lists every account's rows of a writable table (and `users` without hashes, `catalogue_links`, `research_requests`, `workers`, `change_log`), newest first. **Acting for an account** (account views and new rows): an admin agent token may send `X-Carlos-Account: <user id>`; reads, `/api/agent/` writes and research requests then use that account (its listings, its private rows; models still go to the catalogue), and `change_log` records the admin. Other writes with the header get 403.

## Research requests (issue #113)
An account asks for a listing to be researched; a registered worker (`worker.py`, issue #141) does it and writes the car into that account.
- Workers (admin): `GET /api/admin/workers` (each with `status`: `idle`, `working`, `error`, `down` = no heartbeat for 180 s, or `deactivated`; `request_id`, `url`, `username`, `listing_id` of the request it is on; `last_seen`, `last_error`), `POST /api/admin/workers {"name"}` → 201 `{id, token}` (shown once), `POST /api/admin/workers/<id>/token` → a new token (the old one stops working), `PATCH /api/admin/workers/<id> {"is_active": 0|1}`.
- A **worker token** only calls `POST /api/worker/heartbeat {"state": "idle|working|error", "error": "…"}`, `POST /api/worker/claim` and `POST /api/worker/requests/<id>` (only the request it claimed); anything else is 403.
- A **request token** (`request_token` in the claim answer) is the research run's credential: reads and `/api/agent/` POST/PATCH like the worker always did (catalogue rows go to the shared catalogue), listing data only in the requester's account; no admin, settings, queue, deletes or `X-Carlos-Account`; 401 once the request is finished, failed or older than 3 hours.
- `GET /api/requests`: the account's own requests, newest first (`id, url, note, status, requested_at, claimed_at, finished_at, worker, listing_id, result, kind, flag_id, attempts, missing`). Never another account's.
- `POST /api/requests {"url": "https://…", "note": "…"}` → 201 with the request (`QUEUED`). The url may also be `carlos://listing/<id>`, a listing of the account to (re-)research without its ad (the reference car, an ad gone offline, after the research reset; #194). An admin agent token with `X-Carlos-Account: <id>` may queue (and cancel) for that account; `requested_by` then records the admin (NULL = the account itself; issue #139). The URL must be http(s), at most 500 characters; the same URL cannot wait twice; at most 5 requests per account can be `QUEUED` or `RUNNING`.
- `PATCH /api/requests/<id> {"status": "CANCELLED"}`: cancels one of the account's own `QUEUED` requests (400 otherwise).
- `GET /api/admin/requests` (admin): the whole queue with `username`, newest first (last 500).
- `POST /api/worker/claim {"worker": "<name>"}` (worker token, or an admin token the old way; the name is the registered one for a worker token) → `{"request": {...}}` with the oldest `QUEUED` request, now `RUNNING`, or `{"request": null}`. One transaction: two workers never get the same request. A request `RUNNING` for more than 3 hours counts as abandoned and is handed out again. A worker runs one request at a time: when it claims, any request still `RUNNING` under its name (an interrupted run, e.g. a restarted worker) goes back to `QUEUED`, its request token is revoked and `result` says so (issue #160).
- `POST /api/worker/requests/<id> {"status": "DONE", "listing_id": <id>, "result": "…"}` or `{"status": "FAILED", "result": "…"}`, or `{"status": "QUEUED", "result": "…"}` to release it unfinished (usage limit or API error, #206; the worker then waits for the reset) (the worker that claimed it, or an admin token): finishes a `RUNNING` request and ends its request token; `DONE` needs a listing that belongs to the requester. **Done gate (#218):** the server re-grades the listing with the research contract (every item except the owner-only `lst.insurance`); with items `MISSING` the request goes back to `QUEUED` (`attempts` + 1, `missing` = the ids, `listing_id` kept; the claim then returns both and the prompt asks for a continuation run) and after `MAX_ATTEMPTS` (3) it is `FAILED` with the ids. A release (`QUEUED`) is not an attempt; follow-up requests are not graded.
